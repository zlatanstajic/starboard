# Contributing

Contributions are welcome. To propose a change:

1. **Fork and branch.** Fork the repository, then create a branch off `master`. Branch names are kebab-case: lowercase words separated by hyphens, with no underscores or spaces (e.g. `issues/12-short-description`). Only `master` and branches matching `issues/*` run CI, so use the `issues/` prefix to have your push checked automatically.
2. **Set up the project.** Follow the local installation instructions in [README.md](README.md), configure `.env` and `.env.testing`, and never commit either file, credentials, or other local configuration. The Docker image is production-oriented and does not include development dependencies, so use the local Composer setup for development and quality checks.
3. **Work within the existing structure.** Application code belongs in [`app/`](app/), routes in [`routes/`](routes/), frontend code in [`resources/`](resources/), database changes in [`database/`](database/), and tests in [`tests/`](tests/). Reuse existing services, repositories, Blade components, factories, and other shared code before introducing new abstractions. Create Laravel classes with the appropriate `php artisan make:* --no-interaction` command and add new migrations instead of editing migrations that may already have run.
4. **Match conventions.** Follow the style of neighboring files, use explicit PHP parameter and return types, and choose descriptive class, method, and variable names. Tests must be PHPUnit classes. Format changed PHP files with `vendor/bin/pint --dirty`; if frontend assets change, run `npm run build`.
5. **Test before submitting.** Add or update tests for every behavioral change, including happy paths, failure paths, and relevant edge cases. Run the smallest affected test first with `php artisan test --compact tests/path/to/Test.php`, then run the complete quality suite with `composer run test`. The full suite checks Rector, Peck, Pint, PHPStan, PHPUnit, and the required test coverage. The Husky pre-commit hook runs this suite automatically when enabled.
6. **Open a pull request.** Push your branch and open a PR against `master` with a clear description of what changed, why it changed, and how it was tested. Open an issue first for larger changes or changes that affect the project architecture.
